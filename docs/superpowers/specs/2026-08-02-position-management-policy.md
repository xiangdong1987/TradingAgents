# 仓位管理方案（Position Management Policy）

日期：2026-08-02　状态：**P1 已落地（2026-08-04）**；P2/P3 待做

> P1 实现：`assistant/policy.py`（纯函数，六道买入闸 + EUR 快照 + 钳制/定股数）、
> `meta/policy` 配置、策略引擎与 advisor 双路接闸、组合估值改 EUR 统一并修正
> 「EUR 总值 ÷ 原币 N」的量纲错。测试见 tests/test_assistant_policy.py 等。

> 免责声明：本方案是规则框架与工程设计，参数缺省值取自业界常见实践，仅供研究参考，
> 不构成投资建议；所有参数由用户自定，交易由用户自行决策。

## 1. 背景与结论

用户问：TradingAgents 引擎有没有仓位管理方案？经三路代码调查，结论：

- **引擎（tradingagents/）没有可执行的仓位管理**。最终机器可读输出只有 5 档评级
  （Buy/Overweight/Hold/Underweight/Sell）；`TraderProposal` 里的 `position_sizing`
  是可选自由文本（如 "5% of portfolio"），渲染成散文后无下游解析。引擎也没有组合
  状态输入（不知道总值/现金/持仓），原理上无法算头寸。
- **assistant/ 有两条不完整的线**：
  - `advisor.py`：LLM 自由给 `targetWeightPct`，无规则约束、无数值钳制、无现金检查；
  - `strategies/turtle.py`：唯一真正的量化仓位管理（1 单元 = 组合值×1%÷2N，2N 止损，
    ½N 加仓至 4 单元），但只覆盖海龟信号，且组合值多币种直加（无汇率）、不查现金。
- **app/ 撑不起仓位视图**：不解析建议 meta 里的 shares/stop，无权重/集中度展示，
  采纳成交后持仓与现金不自动更新。

所以需要一层**组合级的仓位管理策略（Policy）**，站在引擎评级和海龟信号之上，统一约束
所有建议。

## 3. 方案：三层规则

### 3.1 账户分层（战略配置带）

每个持仓归入一层，各层设目标区间（band）。**区间边界即动作线**（不再额外加缓冲带，
带宽本身已经是免动作区）：

| 层 | 定义 | 目标区间（缺省） |
|----|------|-----------------|
| 防守 | 持有到期国债、债基、债 ETF | 60–85% |
| 核心 | 宽基指数 ETF（VUAA 类） | 10–25% |
| 卫星 | 个股 | 0–15% |
| 现金 | 可用现金 | ≥5% |

BTP 到期兑付是最大的一次性再配置事件：兑付现金按当时的分层缺口再部署，优先补现金
缓冲和核心层；**再配置向导（P3）中写死分散规则——单一发行人直接持券 ≤
maxSingleIssuerPct，不允许一次性滚回同一只新券恢复 60%+ 集中度**。

### 3.2 组合级约束（所有建议统一过闸）

任何来源（advisor / 海龟 / 未来策略）的**买入**建议必须同时满足：

1. **现金充足**：成交后现金 ≥ cashFloorPct（缺省 5%）；不足时建议降级为「需要腾挪
   资金」，资金来源按梯队给候选：① 超上限的持仓 → ② 处于区间内偏上（高于区间中值）
   的层 → ③ 都没有则明示「当前处于存量重排模式，等待 BTP 到期资金」。
2. **单票上限**：个股市值 ≤ maxSingleStockPct（缺省 8%）；单一 ETF/基金 ≤ 25%。
3. **卫星总量**：个股合计 ≤ maxSatellitePct（缺省 15%）。
4. **美元敞口（经济口径）**：底层美元资产合计 ≤ maxUsdExposurePct（缺省 25%）。
   每个标的配 `usdLookthroughPct`（MSFT=100、VUAA=100、EUR 对冲类=0）。
   ⚠️ 已知张力：核心层补到 20%+ 且全用标普类 ETF 时会顶到本上限——届时要么上调
   上限、要么核心层引入非美/对冲宽基分散，由用户决定。
5. **单一发行人（直接持券）**：≤ maxSingleIssuerPct（缺省 40%）。**存量 BTP 白名单
   豁免（只约束新买入）**，到期后新买入受此约束。
6. **总风险预算**：在场风险头寸的理论止损损失合计 ≤ maxTotalRiskPct（缺省 5%）。
   记账规则：每个头寸按 `实际持有股数 × (entry − stop) 折 EUR` 计；存量卫星持仓无
   止损记录的，按 −8% 合成止损纳入；核心/防守层不占风险预算（由分层带宽管理）。
   说明：在缺省参数下**先绑定的约束通常是名义上限（规则 2/3），本条是兜底**——
   防的是上限参数被调松后的总量失控，不提供额外的日常约束感。

**减仓/再平衡**触发（提示，不自动执行）：

- 单票越上限 25%（相对，8%→10%）→ 建议 trim 回上限内；单一基金/ETF 同理
  （25%→31.25%）；
- 层越出目标区间边界 → 建议再平衡（区间即动作线，rebalanceBandPp 缺省 0）；
- 引擎评级降至 Underweight/Sell → 建议减半/清仓（用户决断）。

### 3.3 单笔纪律（每笔买入怎么定股数）

- **三重取小**：
  `股数 = min(风险股数, 上限余量股数, 现金可买股数)`
  - 风险股数 = `(组合值 × riskPerTradePct%) ÷ (entry − stop)`，止损缺省 2N
    （N=20日 ATR），advisor 类建议无 N 时用 −8% 兜底；
  - 上限余量股数 = 规则 2/3/4/5 里最紧的那条允许的增量；
  - **量纲统一**：entry/stop 先按 EURUSD 折成 EUR 再代入（或等价地把风险额折成
    标的币种），跨币种直除是错的。
- **分批建仓**：一次最多 1 个单元，顺势 ½N 加仓（海龟规则），非策略买入也拆 2–3 批。
- **风险预算分母**：可配 `total`（含 BTP，缺省）或 `liquid`（剔除 `holdToMaturity`
  持仓）。当前 BTP 占 63%，用 total 时风险股数几乎总被名义上限截掉（见规则 6 说明）；
  想让风险公式真正起作用，选 liquid 或把 riskPerTradePct 降到 0.5。
- 在本组合规模 + 缺省参数下，海龟的整单元通常放不满名义上限，会被 Policy 截断——
  **这是预期行为**（上限优先于策略信号）。

## 4. 参数（Firestore `meta/policy` 文档，代码内置缺省）

```json
{
  "cashFloorPct": 5,
  "riskPerTradePct": 1.0,
  "riskBase": "total",              // total | liquid
  "maxSingleStockPct": 8,
  "maxSingleFundPct": 25,
  "maxSatellitePct": 15,
  "maxUsdExposurePct": 25,          // 经济口径（穿透底层）
  "maxSingleIssuerPct": 40,         // 直接持券单一发行人；存量白名单豁免
  "issuerWhitelist": ["IT0005696320"],
  "maxTotalRiskPct": 5,
  "rebalanceBandPp": 0,             // 区间边界即动作线
  "trimTriggerRel": 1.25,
  "defaultStop": "2N",              // 无 N 时 -8% 兜底
  "layers": {"defensive": [60, 85], "core": [10, 25], "satellite": [0, 15]},
  "usdLookthrough": {"MSFT": 100, "VUAA.MI": 100}
}
```

持仓新增字段（positions/{ticker}）：
- `layer`: defensive | core | satellite——**缺省用代码内 ticker→layer 映射 +
  「ISIN→defensive」推断**（现有数据无资产类型字段，无法自动分类 .MI 后缀的 ETF
  和个股），用户可在 App 改（P2 出编辑 UI）；
- `holdToMaturity`: bool（riskBase=liquid 的判定依据；缺省仅 IT0005696320 为 true）。

⚠️ 落地前置：`repo.dart` 的 `setPosition` 目前是整文档 `set()`（无 merge），会抹掉
后端写入的 layer/holdToMaturity——P1 必须先改成 merge 写。

## 5. 与现有组件的关系

| 组件 | 现状 | 方案下的角色 |
|------|------|-------------|
| 引擎 5 档评级 | 只有方向 | 提供方向与信念强度，不碰引擎代码 |
| advisor.py | LLM 自由填 targetWeightPct | prompt 注入 Policy 约束 + 返回后**钳制**到规则内 + 现金检查；建议落库补 meta（shares/stop，−8% 兜底） |
| turtle.py | 单标的完整 sizing | 纯函数不变；**engine 按标的币种口径传组合值**（EUR 总值 × 汇率），解决 V_EUR ÷ 2N_USD 的量纲错误；扫描结果过组合级闸 |
| review.py | 只记 14 天涨跌 | 扩展：止损是否触发、按 shares 加权的 € 盈亏（仅对 P1 之后带 meta 的建议生效，存量只有 outcomePct）、风险预算使用率 |
| 组合估值 | 多币种直加（bug） | 统一走 EURUSD 折算（advisor 与 strategies/engine 都修；rebuild_units 只回读已落库 meta，历史账本不受影响） |
| 降级的 buy 建议 | — | 落库时 action 保持 buy 但 meta.blocked=true，engine 去重逻辑跳过 blocked 卡，避免现金腾出后新信号被旧卡挡住 |

## 8. 已知取舍

- 止损检查按日收盘，非盘中实时（与现有 runner 节奏一致）。
- P1/P2 阶段单元账本仍从「已采纳建议」重建，P3 才切换到 trades 实际成交；种子单元
  （存量持仓）n=None 用当前 N 近似，止损/加仓位有系统性误差，属已知近似。
- BTP 按成本计值（无可靠日行情），分层判定接受此偏差。
- 相关性分组（经典海龟的 correlated-market 上限）暂不做，用「卫星总量 + 美元敞口 +
  单一发行人」三个粗颗粒约束近似。
- 债基/债 ETF 的底层国别未穿透（意大利叠加敞口可能高于 63%），P3 之后再议。
